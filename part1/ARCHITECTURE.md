# Part 1 — Architecture

## 1. High-Level Architecture

The `data-sync` service runs as a Kubernetes workload and is managed through GitOps using Argo CD.

```text
                         ┌─────────────────────┐
                         │       Client        │
                         └──────────┬──────────┘
                                    │
                                    ▼
                         ┌─────────────────────┐
                         │ Ingress / LB        │
                         └──────────┬──────────┘
                                    │
                                    ▼
                         ┌─────────────────────┐
                         │ ClusterIP Service   │
                         │     data-sync       │
                         └──────────┬──────────┘
                                    │
                     ┌──────────────┼──────────────┐
                     │              │              │
                     ▼              ▼              ▼
                 ┌───────┐      ┌───────┐      ┌───────┐
                 │ Pod 1 │      │ Pod 2 │      │ Pod 3 │
                 │FastAPI│      │FastAPI│      │FastAPI│
                 └───┬───┘      └───┬───┘      └───┬───┘
                     │              │              │
                     └──────────────┼──────────────┘
                                    │
                                    ▼
                         ┌─────────────────────┐
                         │        Redis        │
                         └─────────────────────┘
```

Production runs multiple replicas to avoid having a single application instance.

## 2. Deployment and GitOps Flow

The deployment configuration is maintained in Git and synchronized to Kubernetes through Argo CD.

```text
Developer
    |
    v
Git Repository
    |
    v
Argo CD
    |
    v
Production Kustomization
    |
    v
Helm Chart + Production Values
    |
    v
Kubernetes Resources
    |
    v
GKE Cluster
```

Argo CD provides:

* automated synchronization
* pruning of removed resources
* self-healing
* declarative desired state

## 3. Helm and Kustomize

Helm provides the reusable workload definition.

The chart contains common Kubernetes resources:

```text
Helm Chart
├── Deployment
├── Service
├── ConfigMap
├── ExternalSecret
├── HPA
├── PDB
└── ServiceMonitor
```

Production-specific values are supplied through:

```text
standard/datasync/production/values.production.yaml
```

Kustomize is used to apply production-specific Kubernetes workload policy.

The current implementation uses Kustomize's Helm integration:

```text
Kustomize
    |
    └── helmCharts
            |
            v
        Helm Chart
            |
            v
      Rendered Manifests
            |
            v
   Production Kustomize patches
```

This allows the reusable Helm chart to remain environment-independent while production placement policy remains in the production Kustomization.

---

## 4. Application Configuration

Non-sensitive configuration is stored in a Kubernetes ConfigMap generated by Helm.

Examples include:

* application environment
* Redis hostname
* Redis port
* log level
* worker count
* maximum connections

The Deployment consumes these values through `envFrom`.

```text
Helm values
     |
     v
ConfigMap
     |
     v
data-sync Pod
```

A checksum of the rendered ConfigMap is included in the Pod template annotation.

Therefore, a configuration change results in a new Pod template and triggers a rolling Deployment update.

---

## 5. Secret Management

Sensitive Redis credentials are not committed to Git.

The production secret flow is:

```text
                    AWS Secrets Manager
                            |
                            | GetSecretValue
                            ▼
                 External Secrets Operator
                            |
                            ▼
                   Kubernetes Secret
                            |
                            ▼
                     data-sync Pod
```

The ExternalSecret maps the `REDIS_PASSWORD` property from AWS Secrets Manager to the Kubernetes Secret consumed by the application.

The secret store uses AWS authentication through EKS Pod Identity.

This avoids storing the actual Redis password in:

* Git
* Helm values
* ConfigMaps
* Deployment manifests

---

## 6. Secret Rotation

Secret rotation is designed as a controlled rolling update.

```text
AWS Secret Updated
        |
        v
External Secrets Operator
        |
        v
Kubernetes Secret Updated
        |
        v
Stakater Reloader
        |
        v
Deployment Restart
        |
        v
New Pod Starts
        |
        v
Readiness Check
        |
        v
Traffic Shift
```

The Deployment uses:

```yaml
maxUnavailable: 0
maxSurge: 1
```

This allows a replacement pod to become ready before an existing pod is removed.

## 7. Application Health

The service exposes:

```text
/health
```

The Deployment uses:

### Startup Probe

Protects applications during initial startup.

```text
Application starts
       |
       v
Startup probe
       |
       ├── Failure → container gets more startup time
       |
       └── Success → readiness/liveness become active
```

### Readiness Probe

Determines whether the pod should receive traffic.

### Liveness Probe

Detects an unhealthy running application and allows Kubernetes to restart it.

## 8. Resource Management

Production defines explicit CPU and memory requests and limits.

```yaml
requests:
  cpu: 500m
  memory: 512Mi

limits:
  cpu: 1000m
  memory: 1Gi
```

Requests allow Kubernetes to make scheduling decisions based on guaranteed resources.

Limits prevent an individual container from consuming unlimited CPU or memory.

---

## 9. Autoscaling

Production uses Horizontal Pod Autoscaling.

```text
                 Metrics Server
                       |
                       v
                     HPA
                       |
              ┌────────┴────────┐
              │                 │
              ▼                 ▼
        Scale Up Pods      Scale Down Pods
```

Production configuration:

```text
Minimum replicas: 3
Maximum replicas: 20
Target CPU:       70%
```

The HPA uses the Kubernetes Resource Metrics API provided by Metrics Server.

Prometheus is used separately for monitoring and alerting rather than as the source of the standard CPU HPA metric.

---

## 10. Workload Availability

Production starts with three application replicas.

The Deployment uses:

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
```

A PodDisruptionBudget is also configured.

Pods are spread across:

```text
topology.kubernetes.io/zone
```

using a topology spread constraint with:

```text
maxSkew: 1
whenUnsatisfiable: DoNotSchedule
```

This reduces the risk of concentrating all application replicas in a single availability zone.

## 11. Security Context

The workload runs with a restricted container security posture.

Pod-level controls include:

```yaml
runAsNonRoot: true

seccompProfile:
  type: RuntimeDefault
```

Container-level controls include:

```yaml
allowPrivilegeEscalation: false

readOnlyRootFilesystem: true

capabilities:
  drop:
    - ALL
```

This reduces the privileges available to the application container.

## 12. Observability

The application exposes Prometheus metrics through:

```text
/metrics
```

A ServiceMonitor allows Prometheus Operator to discover and scrape the application.

```text
data-sync Pod
      |
      | /metrics
      v
ServiceMonitor
      |
      v
Prometheus
      |
      v
Grafana
```

The ServiceMonitor uses a 30-second scrape interval.

Important production signals include:

* request rate
* request latency
* HTTP error rate
* CPU utilization
* memory utilization
* pod availability
* Redis errors
* Redis latency

## 15. Deployment Flow

```text
Git Commit
    |
    v
Argo CD detects desired-state change
    |
    v
Kustomize renders production configuration
    |
    v
Helm renders data-sync resources
    |
    v
Kubernetes applies changes
    |
    v
RollingUpdate
    |
    ├── New pod starts
    ├── Startup probe passes
    ├── Readiness probe passes
    └── Old pod is terminated
```

This provides a declarative, repeatable deployment model while keeping reusable application configuration separate from production-specific workload policy.
